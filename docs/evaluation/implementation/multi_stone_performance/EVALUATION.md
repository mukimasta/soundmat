# Multi-Stone Performance

### Claim

在 Pi 5 上，按 `implementation/DEPLOYMENT.md` 部署的主机系统，垫面上放 10 颗、30 颗乃至 50 颗石头同时演奏时，声音不出现可听见的卡顿或爆音，声音化的节拍不被拖慢；装在花盆空腔里连续运行一小时，不因过热而降频。

### Scope

System / End-to-End：真实的 Pi 5、USB 声卡和音箱，JACK、合成器服务、主机程序全部按部署运行。输入用虚拟垫子按脚本放置石头，保证每次测试可以重复；另外在真实垫子上用实物石头做一次 30 颗的确认。控制台在手机上打开，与真实使用一致。覆盖 Jam 和 Ambient 两种模式。

### Method

每个场景运行 10 分钟，期间记录各项指标，并由人现场试听：

1. **Jam，10 / 30 / 50 颗**：控制区放一颗石头开始播放，其余石头分布在第 2 到 7 环。
2. **Ambient，全部环都有石头**：每环达到最高档位，所有持续、间歇角色都处于激活状态。
3. **频繁变化**：在 Jam 和 Ambient 中，每秒放下或拿起约 5 次石头，检验对账和声部启停的负载。
4. **长时间运行**：Jam 30 颗，装进花盆空腔，盖好毛毡，连续运行 1 小时。

JACK 的缓冲从每块 1024 帧开始测；全部通过后再试 512；未通过时退回 2048，并记录实际采用的设置。

### Metric / Oracle

通过需要同时满足：

1. 10 颗和 30 颗时，10 分钟内音频卡顿（JACK xrun）为 0；50 颗时不超过 1 次，且试听不到爆音或断续。
2. 合成器服务的平均负载低于 60%，峰值低于 85%。
3. 声音化每一拍的计算都在节拍间隔内完成，没有超时的节拍；声音引擎的迟到事件为 0。
4. 一小时长时间运行中 CPU 温度低于 80°C，没有出现降频。
5. 声部让位的次数作为参考记录，不作为通过条件：50 颗时发生让位是预期内的。

### 参考基线

旧版在 Pi 3B 上、JACK 每块 2048 帧时的结果（系列文档第 16 篇，2026-06-03）：50 颗石头时合成器服务约 79%，主循环约 60%，音频卡顿"少见"。

### 未通过时的处理

先看指标定位瓶颈在哪一层，再按以下顺序处理，每一步之后重新评估，通过即停：

1. 降低声部预算。
2. 在音色层面减少运算：检查是否仍有声部自带效果而没有走共用效果；把同时发声的多个音合并成一个声部（旧版对和弦铺底这样做过）。
3. 加大 JACK 缓冲。
4. 用性能剖析确认主机程序的瓶颈后，才在代码层面优化，必要时参考旧版做过的做法（倒排索引、降低灯光合成频率）。

### 结果

正式评估尚未执行，等待 Pi 5 部署完成。

**初步结果（Pi 3B，2026-10-17，不作为通过与否的结论）**：新版装在 Pi 3B 上，真实垫子，所有石头摆满，Jam（Lo-Fi）播放，JACK 每块 2048 帧、48 kHz，以实时优先级运行。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 主机程序 CPU（占单核，平均 / 峰值） | 81% / 120% | 64% / 88% |
| 合成器服务负载 | 约 47% | 约 46% |
| 声音化节拍（期望 60） | 57 | 60 |
| 最近 1 分钟最大节拍延迟 | 34 ms | 20–34 ms，无超过 50 ms |
| 迟到事件、JACK 卡顿 | 0、0 | 0、0 |

按「未通过时的处理」第 4 步，先用性能剖析定位：放满石头时，Jam 灯光图案逐颗灯珠用 Python 计算，占声音化每一拍约 80% 的时间。改为 numpy 整体计算（结果逐像素不变），并把灯光刷新率从 60 降到 30（实物灯带的实际刷新率受控制器循环限制，本来只有约 25–30）。优化后按线程看：声音化约 24%，灯光引擎约 16%，主线程约 10%。旧版第 16 篇的基线是 50 颗时合成器约 79%、主循环约 60%，旧版的 JACK 一直没有实时优先级（新版部署时发现并修正）。
