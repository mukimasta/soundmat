# Philosophy

**处境与问题。** SoundMat 是一件公共艺术装置，会被放在大堂、展厅和拍摄现场，常常没有人看管；它的声音又需要不断打磨。第一版主机程序在三天里写成，能演奏，但四个月后回头看，同一件事在好几处各写一遍，网页上调好的参数重启就丢，串口打不开时会悄悄换成虚拟输入，现场只看到"程序在跑，垫子没反应"。立体声写死在多处，开机自启的配置只存在于一张存储卡上。连作者自己也忘了它是怎么运行的。

**需求与想法。** 我们希望装置插上电就可靠地工作，出了问题能一眼看出是哪里，换一个场地也能被找到和控制。我们希望改声音时只碰声音，在 Mac 上就能听到和装置上一样的结果。我们也希望隔几个月再回来，仍然看得懂、接得上。

**需求本质。** 这几个愿望指向同一个问题：系统里不同性质的变化没有各自的位置。艺术上的调整、系统机制、运行环境，变化的频率和风险都不同，却缠在一起：改一个声音可能牵动串口处理，换一台机器要重新摸索配置，一个环节出错时别的环节替它掩盖。要做的是给每一类变化一个明确的位置，让它只在那里发生。

**核心思路。** 艺术决定只有一个家。响什么、在哪里响、灯怎么亮，都只在声音化里决定；声音化只描述"想要什么"，不碰任何设备，怎样实现交给与音乐无关的引擎。这样打磨声音不会碰坏机制，引擎的改进让所有模式同时受益。声音化内部再把交互逻辑和内容分开：新的声音世界只是新的一份数据。

系统描述"此刻应当如何"，而不是记住"做过什么"。声音化每一拍给出完整的意图，引擎拿它和实际状态对账。系统的正确性因此不依赖过去发出的一串命令：重启、切换、崩溃后的恢复都变成了同一件事，再对账一次。

各部分按自己的节奏运行。传感、声音、灯光的节奏各不相同，传感的节奏甚至由硬件决定；它们之间只交换最新的状态和不能丢失的事件，不互相等待。节奏的精度交给时间戳，而不是交给哪一层跑得准。任何一处变慢或中断，其他部分照常前进。

装置要能照顾自己。它不依赖网络就完整工作，网络只为人服务；服务异常时自动恢复；健康状况，尤其是最容易"看起来在运行却没有声音"的音频链路，要主动说出来，而不是静默地降级。

开发就是在运行真实的系统。开发机上用虚拟垫子运行同一套程序，从垫面状态开始，声音化、引擎、合成器都与装置一致，差异只存在于输入来源和音频设备这样可以替换的边界上。

知识留在项目里。系统配置来自仓库，随时可以重建；设计按层次写在文档里，接手的人不必从代码反推意图。

**如何运转。** 展出前一晚，开发者在 Mac 上用虚拟垫子调整编排，改动只落在编排数据和声音化里，听到的就是装置上的效果。第二天到场插电，系统按仓库里的配置自启，进入默认编排。现场的人连上手机热点，看板上声音一栏是正常的。拍摄途中控制器的线松了一下，声音化照常按节拍推进，音乐和灯光没有停，看板标出链路异常；线插回去后，设备连接自动重连，一切恢复。几个月后有人接手，先读文档就知道要改的东西在哪一层。

**为什么有效。** 每一类变化都有唯一的位置，所以改声音不会波及机制，机制的问题也不会被别处掩盖。描述式的意图和互不等待的节奏，让断线、重启和切换不再需要各自的特殊处理，系统的状态总能从"此刻应当如何"重新得到。健康状况被主动报告，现场的人不需要懂代码也能判断。配置和设计都留在项目里，遗忘不再意味着从头摸索。

**原则与思路。**

1. 艺术决定只在声音化里做；引擎不做艺术决定。
2. 描述此刻应当如何，而不是发出动作指令。
3. 各部分按自己的节奏运行，只交换最新的状态和不能丢失的事件。
4. 新的声音世界只写数据，新的交互逻辑才写代码。
5. 离线优先，装置不依赖网络完整工作。
6. 主动报告健康状况，不静默降级。
7. 开发机和装置运行同一套程序，差异只在可替换的边界。
8. 配置与知识都来自仓库，任何时候都可以重建、可以接手。

一句话说：让每一类变化各得其所，装置才能独自运行，声音才能自由地生长。
