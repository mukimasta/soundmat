# Host Program

本文说明主机程序（Python 包 `soundmat/`）当前的工程实现：怎样运行、模块落在哪些文件、线程怎样分工、配置怎样读取，以及几处需要知道的实现约定。模块职责见 `ARCHITECTURE.md`，模块之间的数据契约见 `system_design/DATA_MODEL.md`，控制接口协议见 `CONTROL_API.md`，控制台见 `CONSOLE_APP.md`。

## 运行

```bash
uv sync                         # 安装 Python 3.12 与依赖
uv run python scripts/compile_instruments.py   # 编译音色（需要 SuperCollider）
uv run soundmat --virtual       # 用虚拟垫子运行；本机没有合成器服务时自己启动 scsynth
uv run pytest                   # 测试
uv run python scripts/render.py meditation scripts/scenes/twenty_stones.json out.wav --stats   # 离线渲染
```

主机程序默认连接本机的 scsynth，开发机上没有在运行的就自己启动一个、退出时一起关掉（见 `SYNTH.md`「运行 scsynth」）；启动后打印控制台的网址：本机 `http://localhost:<端口>`，监听所有网卡时再加局域网名字（`<主机名>.local`）和出口地址。`--no-synth` 改用只记录指令、不发声的声音引擎。不带 `--virtual` 时连接控制器：`--port-serial` 指定串口，默认 `auto` 自动选择（规则见下文「设备连接」）。`--virtual` 用虚拟垫子代替控制器；`--config` 指定其他配置文件；`--data-dir` 指定本机数据目录（设置文件 `settings.json` 和录音，默认是程序目录下的 `data/`，树莓派上是 `/home/soundmat/data`）；`--host`、`--port` 覆盖控制接口的监听地址。控制台需要先在 `console/` 下构建（`npm ci && npm run build`），构建产物由控制接口直接提供；开发控制台时用 `npm run dev`，Vite 把 `/api` 和 `/ws` 转发到 8000 端口。

`scripts/render.py` 不连合成器服务、不出声，按模拟时间运行真实的感知、模式和声音引擎，把一份编排在一张石头时间表上的演奏用 scsynth 非实时渲染成 WAV，并给出渲染用时（折算合成器服务的负载）、声部数、引擎计数，`--stats` 另给响度和电平；需要 SuperCollider 和编译好的音色。时间表格式、原理和负载的折算见 `SYNTH.md`「离线渲染」。

## 线程与数据交换

每种节奏一个线程，控制接口运行在 uvicorn 的 asyncio 事件循环里（主线程）。线程之间只通过 `exchange.py` 的容器交换数据：`Latest` 保存最新值，带版本号，读的一方据此判断有没有新值；`EventHub` 为每个订阅者维护一个 `EventQueue`，订阅者每次取走积累的全部事件，所以多个使用者（声音化、录制）互不影响，事件不会丢失。

当前的线程：

1. **虚拟垫子**（`virtual-mat`）：每秒 60 次产生压力图，在本线程里调用 `Perception.feed` 完成垫面解读，发布快照和事件。真机上由设备连接的读取线程调用同一个入口。
2. **声音化**（`sonification`）：`BeatClock` 每秒 60 拍（配置 `sound.tick_hz`）。每拍取走垫面事件、读取最新快照、调用所有模式实例（切换期间新旧两个），把声音意图交给声音引擎、灯光意图交给灯光引擎，再处理合成器服务的通知、释放淡出完毕的实例，最后交给录制（`after_beat`）。这个线程只做演奏本身和声音化自己的状态（`status.current`、`status.engine`、`status.assets`；模式状态只在变化时写）；电平、控制器链路等状态由别的线程采集。声音引擎不是线程安全的，只在这个线程里调用；切换编排、测试音、设置的应用从其他线程放进队列，在下一拍开始时执行。某一拍的计算超过节拍间隔时不补拍，直接跳到当前时刻。
3. **设备连接**（`device`）：真机上读串口，每收到一帧 S 帧就在本线程里完成垫面信号和垫面解读（代替虚拟垫子线程）。灯光帧由灯光线程直接写串口，写入加锁。
4. **灯光**（`light`）：声音化交出新的灯光意图时立刻合成一帧，没有新意图时按配置 `light.refresh_hz` 继续刷新；刷新率同时是上限，两帧之间至少隔周期的 75%。刷新率设为 30：控制器固件在扫描传感器的同一个循环里刷新灯带，实物灯带的实际刷新率就是传感帧率（约 25–30），发 60 帧只是白算（Pi 3B 上灯光线程因此占约 22% 的核）；合成后写给设备连接，合成结果有变化时同时更新控制台的灯环预览。两个 60 Hz 时钟如果各走各的，会时而把同一份意图合成两次、时而漏掉一份（实测每秒 47 份新意图只有 39 份到达预览），所以由新意图唤醒。
5. **电平采样**（`levels`）：每秒 10 次读取当前编排的电平（`Sonification.sample_levels`），交给控制台的电平条和看板。只读合成器接口缓存的电平，不碰声音引擎。
6. **系统监测**（`monitor`、`monitor-slow`）：每秒采集一次并写入状态中心；较慢的探针（journal、nmcli、tailscale、systemctl、git）在另一个线程里每 10 秒一次，不拖慢每秒的采集。
7. **会话数据写入**（`session-writer`）：录制期间把会话数据逐行写进文件，不阻塞节拍线程。
8. **主线程**：uvicorn 与控制接口。

运行管理把这些服务（虚拟垫子或设备连接、节拍、灯光、电平采样、软件更新的确认、系统监测）放在一个列表里，按顺序启动、按相反的顺序停止。

启动时 `threadnames.install()` 让每个线程把自己的名字设给操作系统（Linux 上用 prctl），所以在树莓派上可以用 `top -H` 或 `/proc/<pid>/task/*/comm` 按线程看 CPU。Pi 3B 上放满石头、Jam 播放时实测（占单核）：声音化约 24%，灯光引擎约 16%，主线程约 10%，设备连接约 7%，系统监测约 4%，合计约 62%。这组数据测于 2026-10-17 的结构调整之前；调整把电平采样和控制器链路状态移出了节拍线程，但它们本来就很轻，开发机上 Jam 放满石头时每拍耗时调整前后都约 0.58 ms，CPU 没有明显变化。

状态中心的订阅回调在修改者的线程里执行；控制接口在回调里只用 `loop.call_soon_threadsafe` 把变化交给事件循环，再由每个 WebSocket 连接自己的推送任务发出。`Latest` 也可以订阅：垫面快照和灯环预览等数据流有新值时同样唤醒推送任务，所以推送跟着数据走，不按固定间隔轮询；状态变化和垫面仍各自限制在 30 次/秒以内。

各条链路的实测帧率用 `rates.py` 的 `RateMeter` 统计（最近 1 秒的次数）。每个模块自己报告自己的帧率和期望值（`rates()`）与累计计数（`counters()`）：设备连接报告传感帧率，感知报告垫面解读，时钟报告节拍和卡住次数，灯光引擎报告合成和写给控制器的帧率，控制接口报告每个 WebSocket 连接实际推送的垫面和灯环，声音引擎报告迟到、让位和放弃。运行管理只在建立系统监测时把这些模块列进 `monitor.Sources`，增加一条链路不需要改运行管理。

## 状态树的写入者

状态树分成若干段，每段只有一个模块写（登记在 `store/branches.py`）：模块建立时用 `Store.writer(...)` 领取自己的段，得到只能写这些段的写入口；被领取的段不能再直接写，同一段也不能被领取两次。声音化写 `status.current`、`status.engine`、`status.assets`，编排目录写 `catalog.arrangements`，录制写 `status.recording` 和 `catalog.recordings`，软件更新写 `status.update`，最近的记录写 `status.log`，设置写 `settings`，其余的 `status.*`（包括控制器链路 `status.mat`）都由系统监测写。测试 `tests/test_state_tree.py` 检查运行中的程序只写登记过的段、每段都有写入者，以及控制台读的每个路径程序都真的写了。

## 配置

`config/soundmat.toml` 在启动时读取一次。压力相关数值在文件里是 ADC 原始读数（满量程 4095），`MatConfig` 换算成归一化压力（读数 / 4095）。文件里出现未知的段或键时启动报错，避免拼错的键被悄悄忽略、装置带着默认值运行。控制台"配置 · 只读"一栏的文字由 `Config.describe()` 生成。

## 区域几何的约定

区域角度沿用第一版的逻辑坐标，因为扇区偏移 4 和灯带偏移 101 都是在这个约定下校准的（见 `DECISION.md` 第 7 条）：外环第 j 区的中心在 j × 11.25°；内环第 j 区就是第一版的第 2j+1 扇区，中心在 (2j+1) × 11.25°。区域的全局序号从第 0 环第 0 区开始依次递增（第 0 环 0–15，第 1 环 16–31，第 2 环从 32 开始，每环 32 个），标识写作"环:环内序号"，例如 `3:7`。

半径取自控制台设计稿的绘图尺寸：环中心半径从 4.0 到 25.75，环宽 2.75，灯环半径 29.15。`Zone.radius` 是除以第 7 环外缘半径后的归一化半径，给空间化使用。

## 去抖的实现

去抖按压力图到达的时刻计算：每个区记住"读数开始与当前状态不同"的时刻，持续达到 `occupy_hold`（放下）或 `release_hold`（拿起）才翻转状态并产生事件，事件时刻是确认的那一帧的时刻。中途读数回到原状态，计时清零。没有新压力图时状态不变，所以控制器断线不会让石头"被拿起"。当前初值是放下 40 ms、拿起 80 ms，尚未在真机上调过（见 `TODO.md`）。

虚拟垫子同样经过去抖。它像控制器一样持续产生压力图，所以点击之后约 40 ms 才出现"放下"，与真机一致。虚拟石头的压力固定为 0.5（约等于读数 2048）。

## 声音引擎的实现

引擎通过 `sound/backend.py` 的 `Backend` 接口发出抽象指令：建立和释放一个模式实例的混音结构、设置它的编排电平和全局参数、开始/修改/淡出/强制释放一个声部、加载和释放素材、设置总输出。声部编号由引擎从 1000 开始分配，正好可以直接用作 scsynth 的节点号。每条指令都带执行时刻：有确定时刻的声音是意图里的时刻加上 `sound.schedule_ahead`（Pi 3B 上 0.15 秒，按 JACK 缓冲取），其余的（没有时刻的预听、参数、淡出、音量）是当前时刻，即立即执行；有时刻的声音主机交出时已经晚过 `sound.late_tolerance`（50 ms）就丢弃。规则见 `system_design/SOUND_ENGINE.md`「定时事件」。之前所有指令都只推后 30 ms，比 Pi 3B 上 85 ms 的音频缓冲还短，scsynth 实测每秒记下约 27 条收到太晚的指令，有节奏的声音因此忽早忽晚；改为现在的规则后降到接近 0。

`RecordingBackend` 是不发声的实现：照单记录指令，并模拟合成器服务的通知——淡出的声部在淡出时长之后结束，单次声音在固定的 2 秒后结束，`simulate_restart()` 模拟合成器服务重启。测试用它检查对账和调度的结果。

已发出的定时事件标识保留 30 秒用于去重。合成器服务重启后引擎调用 `rebuild`：清空声部表，重新设置总输出、建立各实例的混音结构、恢复全局参数，并调用 `on_rebuild` 回调（例如素材库重新加载素材）；下一拍的对账把所有持续声部重新开始。

引擎交给合成器接口的增益有三组：单声道声源用的一组，以及立体声声源左右声道各一组。立体声声源不定位时，左右声道放在房间的左前 330° 和右前 30°（立体声布局下即原样的左右声道）；定位时放在位置两侧各 10°。

空间化公式见 `sound/spatial.py` 的说明：方向上在相邻两只音箱之间等功率分配，再按半径与均匀分布混合，最后归一到等功率。预设布局有立体声（左 330°、右 30°）、四声道（左前 315°、右前 45°、右后 135°、左后 225°）和八声道（0° 起每 45°）。

## 设置与启动

设置保存在数据目录的 `settings.json`，结构与状态树的 `settings` 一致，但只写入改过的项：没改过的项每次启动时取默认值，声音素材库的默认位置因此跟随环境变量 `SOUNDMAT_SOUND` 和程序目录。读取时逐项校验，非法或无法读取的项回到默认值并写一条警告（录音位置和素材库位置必须是绝对路径：相对路径会按工作目录算，装置上那是当前版本的目录，几次更新后旧版本目录被清理，录音就跟着没了）；修改经过 `Settings.update` 逐项校验，任何一项非法就整批拒绝。写入先写同目录的临时文件、`fsync` 后再 `os.replace`，断电时要么是旧文件、要么是新文件。

声音相关的设置（总音量、音箱布局、朝向）变化时，运行管理把应用动作放进声音化的命令队列，在下一拍由节拍线程交给声音引擎。素材库位置变化时编排目录重新检查所有编排的素材；录音位置变化时录制自己刷新录制列表。启动时编排目录播放设置里的默认编排；它不存在时改用第一份能找到的编排，并写一条警告。

## 设备连接与垫面信号

串口协议、选口规则和打开方式沿用第一版：921600 波特；Mac 上只看 `/dev/cu.*`，Linux 上看 `ttyUSB*`、`ttyACM*`、`/dev/serial/by-id/*` 并排除板载 UART；打开时 DTR、RTS 置低；收到第一帧 `S:` 才算控制器就绪并开始发灯光帧，就绪后的第一帧灯光发两次。打不开或没有找到串口时每 2 秒重试；打开后最多等 15 秒收到第一帧（打开串口可能让 ESP32 复位，固件开机约 5 秒的灯效期间不发 S 帧；只等 5 秒的话，每次重开都会在它开完机前再次复位它，在 Pi 3B 上实测会一直重连）；但打开后 3 秒连一个字节都没有就马上关掉重开：ESP32 开机后不停地发数据，不管有没有人读，Pi 开机时串口三十多秒后才有人打开，USB 串口芯片被灌满，第一次打开常常什么都收不到，重开就好（Pi 5 上实测，原来每次开机白等 15 秒）。ESP32 被复位时马上会发开机信息，不会落进这条。收到过之后 5 秒没有 S 帧才关掉重开。校验失败的帧丢弃并计数。链路状态（`DeviceLink.status()`）由系统监测每秒读取，写入 `status.mat`。

垫面信号把 256 个接线读数按预先算好的索引表取成 224 个区域，再做校准（无效读数 −1 当 0、可选反相、除以满量程）。索引表由第一版的映射规则逐步照搬生成：整体先做扇区镜像，外环直接取镜像后的扇区，内环从镜像后的奇数接线扇区读回，最后整体旋转 `sector_offset` 个扇区。需要注意的是，内环在第一版里经过两次镜像，结果其实没有被镜像：内环第 j 个有电极的接线扇区 2k 落在逻辑扇区 2k+1，而外环是反向的。新版照搬了这一行为，是否符合实物需要在真机上核对（见 `TODO.md`）。

灯光引擎把各层按优先级从低到高、按不透明度合成到黑底上；施加偏移时逻辑位置 k 的颜色写到物理灯珠 (k + `led_offset`) mod 108。

## 系统监测

探针都只读，任何一个失败（开发机上没有 JACK、不是树莓派、没装 nmcli）都返回"未知"，不沿用旧值：

| 项目 | 来源 |
|---|---|
| 音频服务是否运行、打开的设备、采样率、缓冲 | 在 `/proc` 里找到 `jackd` 进程，读它的命令行（`-d alsa -d hw:… -r -p -n`） |
| USB 声卡、实际输出设备 | `/proc/asound/cards`，把 JACK 打开的 `hw:` 设备对应到声卡名字；名字或描述里有 USB 即为 USB 声卡 |
| 卡顿次数 | systemd journal 里 jackd 的 xrun 记录数，从主机程序和 JACK 里较晚的那次启动算起、最长一小时（JACK 的启动时刻从 `/proc` 算：树莓派没有电池时钟，systemd 记的启动时间可能还没校时）。重启之前的卡顿不算作现在的问题 |
| 合成器服务收到太晚的指令 | 最近 1 分钟 systemd journal 里 scsynth 的 `late` 记录数（scsynth 每遇到一条就记一行）；达到 5 条时声音一项需要注意 |
| 合成器服务 | `/status.reply`：是否在线、音色是否加载、采样率、平均与峰值负载（另保留最近 60 秒的负载曲线） |
| CPU | 主机程序：`os.times()` 的用户态加内核态时间，两次采集之间的增量除以经过的时间，即占单核的百分比（含所有线程）；整机：`/proc/stat` 第一行的忙碌与总计节拍的增量 |
| 机器 | `/sys/class/thermal`、`vcgencmd get_throttled`、`/proc/meminfo`、数据目录所在磁盘、`/proc/uptime`、`/proc/device-tree/model` |
| 网络 | `nmcli` 当前连接、出口地址、`tailscale status --json`；连接类型按配置 `[network]` 的连接名区分；自建热点开着时，用 `ip -4 neigh show dev wlan0` 数仍有效的邻居条目（约数：离开的设备几分钟后才消失） |
| 主机程序 | 运行时间；自动重启次数来自 `systemctl show -p NRestarts`，服务名是配置 `system.service`，只在 systemd 启动时（有 `INVOCATION_ID` 环境变量）读取；版本先读程序目录的 `VERSION` 文件（部署时写入），没有时用 `git rev-parse` 并标出未提交的改动 |
| 帧率与计时 | 各模块的 `rates()` 与 `counters()`（见上文「线程与数据交换」）、`BeatClock` 的节拍延迟（每拍比计划晚开始多久，最近 1 分钟的最大值）和卡住次数（延迟超过 `sound.late_tolerance`）；监测保留最近 1 分钟的样本，算出增加量。几毫秒的节拍延迟无害：在 Mac 上常见，来自线程等待多睡的几毫秒和 Python 全局锁的轮换，声音都带时间戳并有前瞻和输出延迟，听不出来，所以只统计超过迟到容忍度的「卡住」 |
| 系统时间 | 开机服务 `soundmat-clock` 写下的 `/run/soundmat-clock`：这次开机时系统时钟是否校准过（之后不再校时，见 `DEPLOYMENT.md`「时钟」）；没有这个文件时为未知 |
| 录音空间 | 录音保存位置所在磁盘的可用空间，除以录制的数据速率（当前声道数、是否录分轨） |

状态指示的规则（按顺序，第一条成立的即为结果）：

1. 声音：合成器服务没有响应 → 异常；没有连接合成器服务（`--no-synth`）→ 未知；音色没有加载 → 异常；Linux 上 JACK 没有运行 → 异常；期望 USB 而实际输出设备不是 USB 声卡、或找不到 USB 声卡 → 异常；采样率与期望不同 → 需要注意；当前编排缺少素材 → 需要注意；负载峰值超过 85% → 需要注意；有卡顿（从主机程序和 JACK 里较晚的那次启动算起、最长一小时）→ 需要注意；最近 1 分钟有 3 次以上节拍晚到超过迟到容忍度（50 ms）、合成器服务收到 5 条以上太晚的指令、或有定时事件迟到被丢弃 → 需要注意；主机程序最近 10 秒平均占单核 90% 以上 → 需要注意；主机程序运行不到一小时且被自动重启过、而这次启动不是软件更新安排的 → 需要注意（说明它在一小时内重启过，可能在反复出错；更新切换版本时在 `update.json` 里记下 `plannedAt`，之后两分钟内的启动算作有意的重启）；否则正常。
2. 垫子：使用虚拟垫子 → 正常；控制器未连接 → 异常（原因来自设备连接，例如"没有找到控制器的 USB 串口"）；实测帧率低于 20 → 需要注意。
3. 网络：没有任何出口地址 → 需要注意（装置离线也能演奏，所以不算异常）。

逐声道测试音由 `POST /api/audio/test-tone` 触发：先检查声道（超出音箱布局返回 422），再在节拍线程里让合成器服务在指定的硬件声道上放 1 秒 440 Hz 的正弦波，绕过混音结构和系统音量。

## 录制

录制的状态机在声音化的节拍线程里推进（`Recorder.on_beat` 挂在每拍末尾），但节拍线程从不读写存储卡：按下录制时，在控制接口的线程里检查空间、建好文件夹、启动这段录制的写文件线程；会话数据、录制信息、关闭文件和刷新录制列表都在写文件线程里完成，节拍线程只往它的队列里放东西、给合成器服务发指令。存储卡忙时（例如刚发布完新版本，正在写回大量文件）一次建文件夹就可能卡住好几秒，放在节拍线程里会让演奏停顿（测试 `test_beat_thread_never_touches_the_disk` 守住这一点）。按下录制后：检查剩余空间（按总输出 24 位、分轨 32 位浮点估算，需要能录 10 分钟另加 200 MB 余量，否则拒绝并说明原因）；立即开始 3 秒倒计时，同时让合成器服务打开文件；录音节点和打板提示音都排在倒计时结束那一刻（按时间戳），录音从打板开始，提示音不进录音（见 `SYNTH.md`「录制」）；灯光是录制系统层（优先级最高）。倒计时中按停止时，停止排在录音开始那一刻，不会留下一个停不下来的录音节点。录制中每 0.5 秒检查一次空间，少于 1 分钟时自动停止；合成器服务中断时也停止。停止后写好录制信息，刷新录制列表（`catalog.recordings`）。

一次录制的文件夹 `<录音保存位置>/<YYYY-MM-DD_HHMMSS>_<编排标识>/`：

| 文件 | 内容 |
|---|---|
| `master.wav` | 总输出（硬件输出总线 0…N−1，经过系统音量和限幅），24 位整数 WAV |
| `stems/<总线>.wav` | 各环总线、分组总线和效果返回 `fx`，在模式总处理之前、乘过编排电平；可能超过 0 dBFS，所以是 32 位浮点 WAV |
| `session.jsonl` | 每行一条，带系统时间 `t`：`start`、`pressure`（最多 30 次/秒，压力 × 1000 和有石头的区域）、`event`（放下、拿起）、`sound`（持续声部与全局参数，变化时）、`events`（交出的定时事件）、`light`（灯环颜色，与控制台预览相同的十六进制字符串，每颗灯 6 个字符 rrggbb；最多 10 次/秒）、`slate`、`stop` |
| `info.json` | `startedAt`（带时区的开始时间）、`startSystemTime`、`slateOffsetSeconds`（打板在录音中的位置，固定为 0：文件从打板开始）、`slateSystemTime`、编排、声道数、采样率、格式、开始时的设置、文件清单、`duration`、`endedAt`、`stopReason` |

没有连接合成器服务（`--no-synth`）时也能录制，只产生会话数据和录制信息，`audio` 为 false，不建 `stems/` 目录；文件清单只列实际开始录制的文件。下载接口把整个文件夹边打包边输出为不压缩的 zip，不需要临时文件。
