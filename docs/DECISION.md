# Decision

1. 2026-10-15，数据通路采用异步，不采用帧驱动。直觉上"一帧到达就立刻处理"响应最快。但传感帧率由控制器决定、间隔不均匀，帧驱动会把声音化的节奏绑在传感器上，帧一停音乐和灯光就跟着停。决定：感知按帧更新，声音化按时钟的固定节拍读取最新状态并取走积累的事件，灯光引擎独立刷新，各层只交换最新值。额外等待最多一个节拍，人感觉不到；节奏精度由带时间戳的指令保证。
2. 2026-10-15，开发用的虚拟垫子从感知内部的压力图接入，不模拟控制器和串口。模拟串口能让更多真实代码参与运行，看起来更"完整"。但虚拟垫子的目的是在开发机上方便地开发声音化：鼠标点击就是放石头，声音化、声音引擎和合成器服务与真机一致即可。从压力图接入不需要任何串口或坐标上的特殊处理，复杂度最低。
3. 2026-10-15，SoundMat 系列文档第 12 篇《软件设计与开发》不再作为树莓派程序的现行设计。它写于 2026 年 6 月，混合了对象设计、系统机制和实现细节，并且与新架构不一致。树莓派程序的 System Design 与 Implementation 以本仓库 `docs/` 为准；第 12 篇保留为 6 月版本的历史记录，不随新架构同步修改。
4. 2026-10-15，新版不照搬旧版的性能优化，先不做预先优化，出现卡顿再按评估结果处理。旧版在 Pi 3B 上做过一系列优化（系列文档第 16 篇），重写时自然的做法是把它们全部带过来。但其中一部分已经成为新架构本身的一部分（共用效果、声部预算、每秒 60 拍），一部分在新架构或 Pi 5 上不再需要（浏览器降帧模式、倒排索引、灯光降频、估算声部结束时间），继续保留只会增加复杂度。决定：新版按最直接的方式实现，以 `evaluation/implementation/multi_stone_performance/` 的评估为准，未通过时再按评估中列出的顺序加入优化。
5. 2026-10-16，传感器校准、坐标与灯带对齐、声部上限写成仓库里的固定配置，不在控制台实时调整。原设计和第一版都允许在网页上现场调这些参数。但它们描述的是硬件本身，第一版部署时已经测定（扇区偏移 4、灯带偏移 101、阈值 500 等），换场地也不会变；实时可调要额外维护界面、持久化和变化通知，还会让装置实际运行的参数脱离仓库。决定：作为配置随部署分发，改参数即改仓库并重新部署，控制台只读显示。音箱布局、总音量、默认编排这类随场地变化的参数仍是可调设置。
6. 2026-10-17，手机热点和自建热点的名称和密码直接写进文档，不放进密钥文件。原方案把所有网络密码都放在不进仓库的密钥文件里。但这两个热点只是装置现场的局域网入口，照看装置的人必须知道密码才能连上控制台，密码写在别处反而容易在现场找不到；它们也不通向任何别的资源。决定：手机热点 `soundmat`、自建热点 `SoundMat-AP` 的密码都是 `soundmat`，记录在 `implementation/DEPLOYMENT.md` 的「网络」一节。UW MPSK 的登记密码和 Tailscale 授权密钥仍只放在密钥文件里。
7. 2026-10-17，区域的角度和编号沿用第一版的逻辑坐标，不按新的几何描述重新定义。重写时自然会把内环第 0 区放在 0° 附近、重新约定编号。但第一版部署时校准的扇区偏移 4 和灯带偏移 101 都是在旧坐标下测出来的：外环第 j 区中心在 j × 11.25°，内环有效数据落在旧的奇数扇区上。换坐标就要重新上真机校准。决定：外环第 j 区中心在 j × 11.25°，内环第 j 区即旧的第 2j+1 扇区；灯环逻辑位置 0 在 12 点方向（0°）。改动角度约定时必须同时重新校准这两个偏移。
8. 2026-10-17，控制台以垫面为首页，看板是从底部入口进入的一页，不再是打开时的第一页。原 `design/CONSOLE.md` 让人先看到看板，因为最重要的是看出装置能否正常演奏。设计稿改为垫面即首页、底部"看板 / 录制 / 菜单"三个入口，并把异常原因作为提示条放在垫面页顶部、看板入口上加小点，停在垫面上也不会错过问题。Human 确认按设计稿实现，`design/CONSOLE.md` 随之改写。
9. 2026-10-17，控制台的声音电平按"层"显示，一层一根条，不再每环分左右两半。设计稿里每环两根条（左音箱、右音箱），环名只写在右半边下面；实际看下来名字只写一半显得不对称，写两遍又重复。左右信息在这里用处不大：声音的方位已经由垫面上石头的位置表达，电平条只需要回答"这一层有多响"。同时 Jam 的和声和鼓不属于任何一环，原来根本没有显示，控制环却占着两根不发声的条。决定：一层一根条，名字只写一次；分成"背景"（自己在走的部分）和"石头"（由放置触发的部分）两组，组之间只靠间距分开、不加标题；显示哪些层由编排的 `[meters]` 声明，没有声明时每个发声的环一根（`implementation/ARRANGEMENTS.md`「电平条」）。
10. 2026-10-17，装置的程序更新一律经过 GitHub，但构建在开发机上完成，装置上不构建。原方案是开发机用 rsync 直接把程序推到树莓派；改为经过 GitHub，是为了让装置上运行的每个版本都对应仓库里的一个提交，任何人都能从仓库查到、重现和回退。自然的下一步是让 GitHub Actions 构建发布包，但它每次都要从头装 SuperCollider 和依赖、跑全部测试，一次要 3–5 分钟，开发时太慢；树莓派上又没有 sclang，不能自己编译音色。决定：开发机构建并打包（约 700 KB），作为 GitHub 预发布版本的附件上传，装置从 GitHub 下载安装，前后约 20–30 秒；测试照常由 CI 并行跑，装置不等它。声音素材是例外，体积大、很少变、仓库公开，仍从开发机直接同步。
11. 2026-10-17，状态树的每一段只有一个模块写，并由状态中心强制执行。之前任何模块都能写任何路径：`status.audio` 同时由系统监测、声音化和运行管理写，系统监测还从状态中心读别人写的值来判断健康状态，看板上一个数是谁写的只能靠搜索。决定：在 `soundmat/store/branches.py` 登记每一段和它的写入者；模块用 `Store.writer(...)` 领取自己的段，只能写这些段，同一段不能被领取两次。读取不受限制。各模块的运行数据由模块自己报告，系统监测汇总后写进它自己的段。
12. 2026-10-18，开机时先等系统时钟校准再启动声音，声音启动后这次开机不再校时。默认做法是让系统随时校时、程序自己处理时钟跳变。但树莓派没有电池时钟，开机校时会跳几分钟到几天，而合成器服务按墙钟执行带时间戳的指令，自己要过一分多钟才逐渐跟上跳变；程序层面只能减轻（跳变后一段时间改为立即执行，节奏会松），做不到完全不受影响，在 Pi 3B 上还因此留下过停不下来的声音。决定：开机等校时最多 45 秒（20 秒内没有网络就不等），之后停掉校时服务直到下次开机。代价是没网开机时时间不准，录音的日期时间可能不对，看板会写明。
13. 2026-10-20，内环的坐标按实物改正，不再沿用第一版（修订第 7 条中内环的部分）。在真垫子上沿一条径向线同时按内外环，控制台上内环的位置与外环反向移动：第一版的内环镜像了两次、等于没镜像，而外环是镜像的；内环区的中心也差半个外环区。决定：内环与外环同样镜像、旋转（扇区偏移 4 不变）；内环第 j 区盖住外环第 2j+1、2j+2 区，中心在 (2j + 1.5) × 11.25°，边界与外环边界对齐，和实物一致。外环的坐标和灯带偏移 101 不变；内环的灯光位置跟着区域中心移动，没有单独校准。
