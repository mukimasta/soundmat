11. 在 Mac 上评审后修正了四处：编译脚本只在 Linux 上设置 Qt 的 offscreen 平台（macOS 版 sclang 不带这个插件，会直接退出）；主机名已带 `.local` 时不再追加；底部面板可以按 Esc 关闭，焦点随面板进出；没有音频时录制不建 `stems/`。同时发现设置文件会把没改过的默认值也写进去，声音素材库的位置因此被写死、`SOUNDMAT_SOUND` 失效，改为只保存改过的项。README 的快速开始按 macOS 逐步核对后重写。
12. 第九阶段（在本地完成）：灯环预览、电平条和看板。实测控制台每秒只收到约 23 帧灯环数据：灯光引擎是 60 Hz，但预览被限到 30 Hz，控制接口又按 30 Hz 轮询，两边节奏错开会丢帧。改为预览与灯光同频，推送由数据变化唤醒，颜色编码成十六进制字符串（每帧约 650 字节）；控制台把灯环拆成单独的组件，每帧只重画灯珠。之后又发现声音化和灯光引擎两个 60 Hz 时钟之间也在错拍（每秒 47 份新灯光意图只有 39 份到达预览），改为新意图到达时立刻合成，修正后两者一致。电平条改为一层一根、由编排声明分组（`DECISION.md` 第 9 条），Lo-Fi 的和声和鼓第一次显示出来。看板新增"节奏"卡（各条链路的实测与期望帧率、节拍超时、迟到），以及连接类型、自建热点上的设备数、主机程序运行时间与自动重启次数、程序版本、还能录多久；最近 1 分钟节拍晚到超过 50 ms 有 3 次以上或有迟到、或主机程序一小时内被自动重启过。最初按"节拍超时"（某一拍晚到挤占了下一拍）报警，在 Mac 上开着 scsynth 实测每分钟 79 次，而节拍率仍是 60、迟到为 0：这些超时只是线程调度和 Python 全局锁带来的几毫秒延迟，有前瞻和输出延迟兜着，不影响声音，所以改为按真正可能让声音迟到的延迟判断，声音一项记为需要注意。
13. 开发机上恢复一条命令运行：`uv run soundmat` 先看配置的端口上有没有 scsynth，有就连，没有就自己启动、退出时一起关掉；树莓派上仍由 systemd 管 scsynth，在 systemd 下从不自己启动。启动时打印控制台的本机和局域网网址。顺带发现连真实 scsynth 的两个测试在开发机上会连上正在试听的 scsynth、清空它的节点树，改为需要显式打开。
14. 程序更新改为经过 GitHub：开发机上的 `scripts/release.py` 推送、构建、打包（约 700 KB）并作为预发布版本上传，装置在控制台的"软件更新"里（或由发布命令通知）从 GitHub 下载安装，按版本目录存放、切换后由 systemd 重新启动，新版本反复起不来时由启动保护切回上一版（`DECISION.md` 第 10 条）。写测试时发现 `uv sync` 必须在版本目录的最终位置执行：环境里的脚本写死了所在路径，先在临时目录建好再改名，新版本会根本起不来。
15. 新版第一次上真机：装在 Pi 3B 的 `~/sm/` 版本目录里，第一版保留为 `soundmat-v1.service`，用发布命令从 GitHub 更新，全程约 38 秒。部署时查出五个问题：第一版的 JACK 服务缺 `LimitRTPRIO`，JACK 几个月来一直没有实时优先级，很可能是第一版卡顿的原因之一；logind 的 `RemoveIPC` 在 SSH 退出时清掉 JACK 的信号量；控制器在打开串口后只等 5 秒首帧，打开串口又会让 ESP32 复位、开机灯效约 5 秒不发数据，于是反复复位、永远连不上（改为 15 秒）；系统监测解析不了 `-dalsa` 这种连写参数；更新导致的重启被当成出错。JACK 改为 48 kHz，新版网络方案（含 Avocado）也装上了 Pi 3B。实测传感帧率 25–30 fps。此前以为的爆音是音箱的问题。
16. 性能（Pi 3B，所有石头摆满，Jam 播放）：主机程序平均占单核 81%、峰值 120%，节拍掉到 57。性能剖析发现 Jam 灯光图案逐颗灯珠用 Python 计算，占每一拍约 80% 的时间；改为 numpy 整体计算（逐像素与原来一致），并把灯光刷新率降到 30（实物灯带本来只有约 25–30 帧），降到平均 64%、峰值 88%，节拍稳在 60。为此看板加上主机程序和整机的 CPU，运算负载仪表改为显示合成器和主机程序中更高的一个；各线程的名字设给操作系统，可以按线程看 CPU。详见 `evaluation/implementation/multi_stone_performance/` 的初步结果。
17. 架构整理（不改变装置的行为）：
    - **运行管理**改为只做组装：按依赖顺序建立、连接，按顺序启动、按相反顺序停止。之前它还管着编排目录、链路状态推送、电平采样、给看板拼运行数据。编排目录移到 `sonification/catalog.py`，素材的加载和释放回到声音化。各模块自己报告帧率和计数（`rates()`、`counters()`、`status()`），系统监测通过 `monitor.Sources` 读取；录制只接收它用到的模块，不再是 15 个参数和回调。
    - **节拍线程**只做演奏本身。电平采样移到单独的线程（每秒 10 次），控制器链路状态改由系统监测每秒读取，系统监测里较慢的探针移到另一个线程。开发机上实测每拍耗时前后都约 0.58 ms：移出去的事本来就很轻，这一项是结构上的整理，不是性能优化。
    - **状态树**每段只有一个写入者，登记在 `store/branches.py`，由状态中心强制执行（`DECISION.md` 第 11 条）。`status.audio.engine` 和 `status.audio.assets` 因此改为 `status.engine` 和 `status.assets`。新测试检查控制台读的每个路径程序都真的写了。
    - **其他**：
        - 意图（`intent.py`）移出声音化，同时解开了声音引擎与声音化之间的循环导入。
        - 系统时间放到最底层的 `timebase.py`。
        - `errors.UserError` 统一了编排、录制、更新、设置的拒绝原因，控制接口用一个处理器转成 HTTP 状态码。
        - `Backend` 接口补上 `status()` 和 `records_audio`，不再按类型判断。
        - Jam 和 Ambient 共用一套向量化的灯光画布，两者都与原来逐灯珠的画法逐像素对照。
        - 去掉不影响声音的"节拍超时"计数。
        - 删除第一版的 `SETUP.md`。
18. 节奏不稳的原因找到了：不是主机卡，是提前量不够。用户说峰值时"节奏不稳"，但看板上主机的节拍延迟和迟到一直正常。在 Pi 3B 上读 scsynth 的日志发现，它每秒记下约 27 条收到太晚的指令（大多晚 60–100 ms）：Pi 3B 上 JACK 的缓冲是 2 × 2048 帧 = 85 ms，scsynth 要在缓冲开始计算之前收到指令，而主机所有指令只推后 30 ms，有节奏的声音也只有约 130 ms，贴着底线，稍有延迟就被挪到下一个缓冲。在装置上把提前量临时改成 0.15 秒，迟到降到 0，但放下石头的预听明显变慢。最后定的规则是：有确定时刻的声音（鼓、和声、扫描命中）统一推后 `sound.schedule_ahead`（0.15 秒），其余的（预听、参数、淡出）一律立即。意图里由"给不给时刻"说明，引擎照此执行；已经排好、还没开始的声部之后的指令不早于它的开始时刻；Jam 的扫描灯光和闪光按听到的时刻画。scsynth 收到太晚的次数从此显示在看板的"节奏"卡上，原来的看板看不到这个问题。
19. 发布到 Pi 3B 后，scsynth 的迟到降到 0，但仍偶尔有扰动和毛刺。逐项排查：迟到、xrun、声部让位都是 0，没有欠压和降频。抓总输出电平发现，Jam 播放时总输出几乎一直贴在限幅值 −1 dBFS（40 秒里 387 个样本有 358 个），反推限幅前各层相加的峰值约 +7 到 +11 dBFS。各环增益沿用第一版，而第一版的总输出没有限幅器，超出的部分直接削波，当时以为是音箱的爆音，很可能就是这个。新增编排的整体电平 `level`（dB），由声音引擎乘在这份编排的混音总增益上，Lo-Fi 设为 −12 dB。音量降到约 25% 试听后明显好转，剩下极少数一两个音"爆一下、不完整"，程序里所有能看到的指标都正常，最可能是 Pi 3B 上 USB 声卡与控制器共用的老 USB 控制器偶尔丢包，留待换到 Pi 5 后确认。同时把总音量从编排面板挪到首页。
20. 看板按层次重新组织。原来结论之后的各组都用同一种卡片平铺，"卡顿"（结果）、"缓冲"（配置）、"因预算放弃"（内部计数）摆在同一层，看不出主次。改为三层：结论和三个状态指示；每部分一张只放看得懂的关键信息的卡片（声音卡片上的结果是卡顿和迟到，配置出问题时才以提示出现）；最下面默认收起的"详细信息"，用不分卡片的分组列表放音频配置、帧率表和内部计数；机器一组（内存、存储、CPU、运行时间、重启、版本）照看时常看，按用户意见保留完整卡片（`design/CONSOLE.md`「看板」）。
21. 在 Pi 3B 上切到《京都岚山》时机器卡死，合成器服务两次被内核因内存不足强制结束。《京都岚山》的 14 个素材解码后共 415 MB，其中三段长环境声占 276 MB；Pi 3B 共 905 MB，其他部分已用约 330 MB，内存压缩交换（zram）让机器先卡死再结束进程。配置的素材预算 768 MB 是按 Pi 5 定的。决定 Ambient 只在 Pi 5 上运行，Pi 3B 不加专门的处理。同时排查录音位置：默认就是数据目录下的绝对路径，更新不会删掉录音；但设置里若改成相对路径会落进版本目录，现已要求录音位置和素材库位置必须是绝对路径。
22. 录制改为倒计时结束、打板那一刻才开始录：之前按下就开始录，倒计时的 3 秒和提示音都在文件开头，用户听录音时觉得多余。现在提示音只在现场响（直接写到硬件输出、排在录音节点之后），给摄像机录到；录音文件从同一时刻开始，剪辑时把文件开头对到视频里那一声即可，对齐精度不变。同时"已录制"里可以删除录制（再点一次确认）。
23. 发布后的第一次录制在 83 毫秒后被判为"合成器服务中断"而停止，文件里留下一段提示音。查日志发现节拍线程在开始录制时卡了约 6 秒：建文件夹、开文件、写录制信息都在节拍线程里，而刚发布完新版本、存储卡正在写回大量文件。卡住期间没有向合成器服务发 `/status` 查询，恢复后按"2 秒没收到回复"判定离线，停掉了录音并重建了混音结构，合成器服务其实一直正常。两处都改了：录制的文件操作全部移出节拍线程（按下录制时在控制接口线程里建文件夹，其余交给写文件线程）；离线改按"发出的查询 2 秒没有回复"判断。
24. 控制台加上重启：菜单里的"重启"有重启声音、重启程序、重启机器三项（从轻到重，各写明中断多久，再点一次确认），声音出问题时首页的问题提示条上也出现入口；三种重启都交给 systemd，装置用户的权限由 `system/polkit/50-soundmat.rules` 只放开这几项。同时，看板上的卡顿改为从主机程序和 JACK 里较晚的那次启动算起、最长一小时：用户重启后看到"最近一小时卡顿 55 次"，那是重启前的事，不该算作现在的问题。推送后 CI 的测试真的去执行了 `systemctl restart`（被拒绝，没有影响）：判断"是否在装置上"原来看 `INVOCATION_ID`，而 CI 机器本身也由 systemd 运行；改为看主机程序自己的 cgroup 是不是 `soundmat.service`。Pi 3B 上的素材随后删除，给录音腾出空间，它只跑 Jam。
25. Pi 3B 重启机器后、石头一直摆在垫子上的情况下开始播放，严重卡顿：Jam 放完后 scsynth 里还留着 7 个和声铺底，负载 80%，JACK 两分钟里记了约 300 次 xrun。原因是重连时清空节点树之后，排在未来时刻的旧指令照常执行，而主机程序分配混音组编号的计数器在重连时被归零，新组和旧组同号，旧指令就把和声铺底建进了新组，成了没人释放的节点；定时声音的提前量加到 0.15 秒后，这个窗口变大了。改为节点编号永不重复使用（`ScsynthBackend._node`），旧指令指向已经不存在的组，被 scsynth 丢弃。没能在 Pi 上复现到重连发生的那一刻（之后 Pi 离线，日志未保存），修复依据是代码与现象的对应。
26. 第 25 条的推测没有解释这次卡顿。Pi 3B 再次开机后同样卡死，这次日志还在：开机约 30 秒后联网校时，墙钟一下往前跳了 276 秒；19 秒后出现第一次 xrun，之后和声铺底越积越多，scsynth 负载升到 97%。真正的原因：scsynth 要过约 20 秒才跟上墙钟的跳变，这期间带时间戳的"开始"在它看来都在 4 分多钟以后、被压住，而和声铺底的"停止"是立即发的，先执行、落空；等 scsynth 对齐后，被压住的"开始"放出来，铺底就再也没人停。改了两处：一个声部之后的修改、停止、让位跟着它开始时的方式走（按时刻开始的，后续指令也按时刻排，`SOUND_ENGINE.md`「定时事件」）；检测到墙钟跳变后 25 秒内所有指令一律立即执行。第 25 条的编号不重复使用仍然保留，它堵住的是另一条同样会留下孤儿节点的路。
27. 用户认为程序层面"跳变后立即执行"的保护不够：节奏仍会受影响。改为从源头避免声音运行时时钟跳变：开机服务 `soundmat-clock` 在 JACK 之前运行，有网就等校时完成（最多 45 秒），20 秒没网就不等，然后停掉校时服务直到下次开机（`DECISION.md` 第 12 条、`DEPLOYMENT.md`「时钟」）。看板「机器」显示这次开机时系统时间是否校准过。在 Pi 3B 上实测（2026-10-18 02:19，石头一直摆着、开机即播放 Jam）：时钟服务等了 19 秒校时完成，1 秒后 JACK、合成器服务、主机程序依次启动；之后一分钟 xrun 0、合成器收到太晚 0，没有残留节点。装的时候发现 Pi 3B 的 `jackd.service` 是第一版留下的，改用覆盖文件 `jackd.service.d/after-clock.conf` 让它排在时钟服务之后；拷到 `/tmp` 的文件重启就会被清空，要在重启前装好。同一天的另一次开机（时钟服务还没装上，校时跳了 12.9 秒）实测到 scsynth 是在约一分半钟里逐渐对齐时钟的，期间指令最多晚 2.7 秒，并非之前以为的约 20 秒一次对齐；程序里跳变后改为立即执行的宽限期据此从 25 秒改为 120 秒。随后按用户意见删掉了这层"跳变后立即执行"的保护：开机等校时之后，声音运行时时钟不会再跳，保护不会触发；保留的是同一个声部的指令统一时间方式和节点编号不重复使用，这两项本身就是正确的做法。
